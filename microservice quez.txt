                Q5. Explain DTO pattern ?
                            - The Data Transfer Object (DTO) pattern is a design pattern that allows you to transfer data between different parts of your application. 
                            - DTOs are simple objects that contain only data, and they do not contain any business logic. 
                            - This makes them ideal for transferring data between different layers of your application, such as the presentation layer and the data access layer.
                            - Here are some Of the benefits Of using the DTO pattern:
                                      - Reduces network traffic: 
                                                     • DTOs can be used to batch up multiple pieces of data into a single object, which can reduce the number of 
                                                       network requests that need to be made. 
                                                     • This can improve performance and reduce the load on your servers.
                                      - Encapsulates serialization:
                                                     • DTOs can be used to encapsulate the serialization logic for transferring data over the wire. 
                                                     • This makes it easier to change the serialization format in the future, without having to make changes to 
                                                       the rest of your application.
                                      - Decouples layers: 
                                                     • DTOs can be used to decouple the presentation layer from the data access layer. 
                                                     • This makes it easier to change the presentation layer without having to change the data access layer.

                                                                 • Based on these events, we can identify:
                                                                                               Commands,
                                                                                               Reactions
                                                                 • We can then group these events together and try to create domain-driven services.

                Q2. What is Strangler Fig pattern and when to use Strangler Fig pattern?
                             - The Strangler Fig Pattern is a software migration pattern.
                             - used to gradually replace or refactor a legacy system with a new system, piece by piece, without disrupting the existing functionality.
                             - The Strangler Fig Pattern facilitates the migration of a monolithic application to a modern microservices architecture by leveraging 
                               a Domain-Driven Design (DDD) approach.
                             - This pattern gets its name from the way a strangler Fig plant grows around an existing tree, slowly replacing it until the original 
                               tree is no longer needed.
                             - A Strangler Facade is introduced to route traffic between the legacy monolithic application and the new microservices. 
                               During this phase, both the monolith and microservices coexist.
                             - As the microservices are developed and stabilized, the corresponding functionality in the monolith is gradually phased out and 
                               eventually removed. This process involves four key steps: Identification, Transformation, Co-existence, and Elimination.
                             - When to Use the Strangler Fig Pattern:
                                     - When you need to modernize a large or complex legacy system.
                                     - When you want to avoid the risk associated with a complete system rewrite or "big bang" migration.
                                     - When the legacy system needs to remain operational during the transition to the new system.

                Q2. What is software containerization ?  
                            - Software containerization is an OS virtualization method that is used to deploy and run containers without using a virtual machine (VM). 
                            - Containers can run on physical hardware, in the cloud, VMS, and across multiple OSs.
                            - What Exactly happens in containerization :
                                            - Containers are based on the concept Of operating system (OS) virtualization, where multiple containers can run on 
                                              the same physical or virtual machine, sharing the same OS kernel. 
                                              This differs from traditional virtualization, where each virtual machine (VM) runs a separate OS instance.
                                            - In containerization, Linux features such as namespaces and cgroups play a crucial role in providing isolation 
                                              and resource management. 
                                              Here's a brief explanation of these concepts:
                                                         - NAMESPACES :
                                                                - Linux namespaces allow for the creation of isolated environments within the operating system. 
                                                                - Each container has its own set of namespaces, including process, network, mount,
                                                                  IPC (interprocess communication), and user namespaces.
                                                                - These namespaces ensure that processes within a container are only aware of and can interact with
                                                                   resources within their specific namespace, providing a level of isolation
                                                         - CONTROL GROUPS :
                                                                - cgroups provide resource management and allocation capabilities for containers.
                                                                - They allow administrators to control and limit the resources (such as CPU, memory, disk I/O, and

                                                                -  By using cgroups, container runtimes can enforce resource restrictions and prevent one container from
                                                                   monopolizing system resources, ensuring fair allocation among containers.

SECTION 05 :
        DEEP DIVE ON CLOUD NATIVE APPs & 15-Factor Methodology
--------------------------------------------------------------
                Q1. What are cloud native applications ?
                                - Cloud-native applications are software applications designed specifically to leverage cloud computing principles and take
                                  full advantage of cloud-native technologies and services. 
                                - These applications are built and optimized to run in cloud environments, utilizing the scalability, elasticity, and flexibility 
                                  offered by the cloud.
                                - NOTE:- Spring Cloud technologies are commonly used to build cloud-native applications.
                                - Important characteristics of cloud-native applications :
                                              • Microservices :
                                                     Often built using a microservices architecture,where the application is broken down into smaller, loosely coupled 
                                                     services that can be developed, deployed, and scaled independently
                                              • Containers :
                                                     Typically packaged and deployed using containers, such as Docker containers. Containers provide a lightweight and consistent 
                                                     environment for running applications, making them highly portable across different cloud platforms and infrastructure
                                              • Scalability & Elasticity :
                                                     Designed to scale horizontally, allowing them to handle increased loads by adding more instances Of services. 
                                                     They can also automatically scale up or down based on demand, thanks to cloud-native orchestration platforms like
                                                     Kubernetes
                                              • DevOps Practices :
                                                     Embrace DevOps principles, promoting collatnration between development and operations teams. 
                                                     They Often incorporate continuous integration, continuous delivery, and automated deployment pipelines to
                                                     streamline the software development and deployment processes.
                                              • Resilience & Fault Tolerance :
                                                     Designed to be resilient in the face of failures. They utilize techniques such as distributed architecture,
                                                     load balancing, and automated failure recovery to ensure high availability and fault tolerance.
                                              • Cloud-Native Services :
                                                     Take advantage Of cloud-native services provided by the cloud platform, such as managed databases, messaging queues, 
                                                     caching systems, and identity services. This allows developers to focus more on application logic and less on 
                                                     managing infrastructure components.
                                - Development Principles or guide line of building Cloud Native: 12 Factors & Beyond :
                                              - The engineering team at Heroku, a cloud platform, introduced the 12-Factor methodology, a set of development principles
                                                designed to guide the development and deployment of cloud-native applications. As technology evolved and new tools, 
                                                practices, and requirements emerged, the original 12-Factor methodology was expanded by Kevin Hoffman in his book 
                                                'Beyond the Twelve-Factor App'. He introduced three additional factors and updated the existing principles to better 
                                                address modern application development needs. This revised approach is known as the 15-Factor methodology.
                                              - 15-Factor methodology :
                                                            1. One codebase, one application
                                                            2. API first
                                                            3. Dependency management
                                                            4. Design, build, release, run
                                                            5. Configuration, credentials & code
                                                            6. Logs
                                                            7. Disposability
                                                            8. Backing services
                                                            9. Environment parity
                                                            10. Administrative processes
                                                            11. Port binding
                                                            12. Stateless processes
                                                            13. Concurrency
                                                            14. Telemetry
                                                            15. Authentication & authorization
                                              • One codebase, one application :
                                                       - Each application should have its own codebase, stored in its own repository.
                                                       - The same codebase can be used for multiple deployments/environments without rebuilding the application.
                                                       - Example: An Accounts microservice has one Git repository, and the same code is deployed to development,
                                                                  testing, and production environments.
                                              • API first :
                                                       - Design the API first before building the application, so other teams/services can use it easily.
                                                       - It helps teams work independently and allows internal changes without affecting applications that use the API.
                                                       - Example: An Accounts Service first defines APIs like /accounts and /accounts/{id}, then other teams can
                                                                  build their services using these APIs.
                                              • Dependency management :
                                                       - All application dependencies should be clearly listed in a manifest file and managed by tools like Maven or Gradle.
                                                       - Dependencies should be downloaded and managed automatically instead of being handled manually.
                                                       - Example: In a Spring Boot application, dependencies like Spring Web and Spring Data JPA are added in
                                                                  pom.xml, and Maven downloads them automatically.
                                              • Design, build, release, run :
                                                       - Application development is divided into 4 separate stages: Design → Build → Release → Run.
                                                       - Each stage has a specific purpose, and the build/release should be fixed and uniquely identified so the same
                                                         version can be safely deployed and reproduced.
                                                       - Example: Developers design the application → Maven builds a JAR → version 1.0.0 is released →
                                                                  the same JAR is run in the production environment.
                                              • Configuration, credentials & code :
                                                       - Configuration and credentials should be kept separate from the application code and managed externally,
                                                         preferably using environment variables.
                                                       - This allows the same application code to be deployed in different environments without rebuilding it.
                                                       - Example: Database username, password, and URL are stored as environment variables instead of writing
                                                                  them directly in application.properties.
                                              • Logs :
                                                       - Applications should write logs to standard output (stdout), while an external log aggregator like Loki or
                                                         ELK (Elasticsearch, Logstash, Kibana) handles log storage, collection, and viewing.
                                                       - Example: A Spring Boot application writes logs to stdout → Loki collects and stores the logs →
                                                                  Grafana is used to view them.
                                              • Disposability :
                                                       - In cloud-native applications, application instances should be easy to start and stop when needed.
                                                       - They should start quickly to handle increased load and shut down gracefully so ongoing requests or jobs can
                                                         finish properly.
                                                       - Example: Kubernetes can quickly start new application instances when traffic increases and replace failed
                                                                  instances automatically.
                                              • Backing services :
                                                       - Backing services are external resources that an application depends on, such as databases, message brokers,
                                                         caches, or APIs.
                                                       - They should be treated as attached resources, so they can be replaced or changed without modifying the
                                                         application code.
                                                       - Example: A local MySQL database can be replaced with an AWS database by changing the connection
                                                                  configuration, without changing the application code.
                                              • Environment parity :
                                                       - Environment Parity means keeping development, testing, and production environments as similar as possible
                                                         to avoid unexpected issues during deployment.
                                                       - It reduces time, people, and tools gaps between environments.
                                                       - Example: Using the same PostgreSQL version in development, testing, and production instead of H2 locally
                                                                  and PostgreSQL in production.
                                              • Administrative processes :
                                                       - Administrative or management tasks like database migrations, batch jobs, and maintenance tasks should be
                                                         treated as separate processes and run in the same environment as the application.
                                                       - Example: A database migration can run as a separate one-time process, complete the task, and then stop.
                                              • Port binding :
                                                       - Port Binding means a cloud-native application exposes its service through a specific port and can run
                                                         independently without relying on an external server like Tomcat.
                                                       - Example: A Spring Boot application uses an embedded Tomcat server and runs on port 8080, so users or other
                                                                  services can access it through that port.
                                              • Stateless processes :
                                                       - Stateless Processes means each application instance should not store user or application data locally.
                                                       - Any required state should be stored in an external backing service like a database, so any instance can be
                                                         replaced or scaled without losing data.
                                                       - Example: A Spring Boot application stores user/session data in a database or Redis instead of keeping it
                                                                  inside the application instance.
                                              • Concurrency :
                                                       - Concurrency means an application should be able to handle multiple tasks or user requests at the same time.
                                                       - It helps the application scale horizontally by running multiple processes/instances to handle increased workload.
                                                       - Example: A Spring Boot web application uses multiple threads from a thread pool to handle many HTTP requests
                                                                  at the same time.
                                              • Telemetry :
                                                       - Telemetry means collecting data from an application so we can monitor its health, performance, and behavior
                                                         remotely. Common telemetry data includes logs, metrics, traces, health status, and events.
                                                       - Example: Spring Boot sends logs, metrics, and traces to tools like Grafana, Prometheus, and Tempo for monitoring
                                                                  and troubleshooting.
                                              • Authentication & authorization :
                                                       - Authentication checks who the user is, while Authorization checks what the user is allowed to do. Together,
                                                         they help secure the application using a zero-trust approach.
                                                       - Example: A user logs in with username/password → Authentication verifies the user → Authorization checks
                                                                  whether the user can access an admin API.

                     - JVM System Properties?
                          - JVM System Properties are key-value pairs provided to the JVM at application startup.
                          - They are used to configure the Java application without modifying the code.
                          - In plain Java, they can be accessed using System.getProperty().
                          - In Spring Boot, we usually don't call System.getProperty() directly because Spring Boot automatically loads JVM System Properties into the Spring Environment.
                          - These values can be accessed using:
                                                        @Value
                                                        Environment
                                                        @ConfigurationProperties
                          - JVM System Properties are passed using the -D option.
                          - Example:
                                java —Dspring.jpa.show—sql = false jar jobportal.jar

                     - Environment Variables?
                           - Environment variables are operating system-level variables used to store configuration outside the application.
                           - They are popular for external configuration because they work across all operating systems.
                           - In plain Java, they can be accessed using System.getenv().
                           - In Spring Boot, we usually don't call System.getenv() directly because Spring Boot automatically loads environment variables into the Spring Environment.
                           - These values can be accessed using:
                                                               @Value
                                                               Environment
                                                               @ConfigurationProperties
                           - To map an environment variable to a Spring property:
                                      Change letters to uppercase

                                                                   'This automatic conversion is called relaxed binding in Spring Boot.'

                Q14. Drawbacks of externalized configurations using springboot alone ?
                           - CLI arguments, JVM properties, and environment variables are effective ways to externalize configuration and maintain the immutability of

                             which can introduce potential errors during deployment.

                Q28. Explain liveness and readness probes ? 
                         NOTE:- ye general topic hai ye tools like, docker,kubernetes and cloud platfor me use hota hai. or yha cloud config ke liye.
                            - Liveness :
                                      - A liveness probe sends a signal that the container or application is either alive (passing) or dead (failing).
                                      - If the container is alive, then no action is required because the current state is good.
                                      - If the container is dead, then an attempt should be made to heal the application by restarting it.
                                      - In simple words, liveness answers a true-or-false question: "Is this container alive?"
                            - Readiness :
                                      - A readiness probe used to know whether the container or app being probed is ready to start receiving network traffic.
                                      - If your container enters a state where it is still alive but cannot handle incoming network traffic (a common scenario during startup), 
                                        you want the readiness probe to fail. So that, traffic will not be sent to a container which isn't ready for it.
                                      - In simple words, readiness answers a true-or-false question: "Is this container ready to receive network traffic ?"

                       NOTE:- Inside Spring Boot apps, actuator gathers the "Liveness" and "Readiness" information from the ApplicationAvailability

                                                                                                  jagah/database jahan services ki information store hoti hai )

                                                     - Microservices/clients that connect to the central server to deregister their address when they are about to shutdown

                Q17. What is Eureka self-preservation mode ?
                             - In a distributed system using Eureka, each service instance periodically sends a heartbeat signal to the Eureka server to indicate that 
                               it is still alive and functioning. If the Eureka server does not receive a heartbeat from a service instance within a certain timeframe,
                               it assumes that the instance has become unresponsive or has crashed. In normal scenarios, this behavior helps the Eureka server maintain
                               an up-to-date view Of the registered service instances.
                             - However, in certain situations, network glitches or temporary system delays may cause the Eureka server to miss a few heartbeats, leading
                               to false expiration of service instances. This can result in unnecessary evictions of healthy service instances from the registry, 
                               causing instability and disruption in the system.
                             - TO mitigate this issue, Eureka enters into Self-Preservation mode. When Self-Preservation mode is active, the existing registry entries 
                               will not be removed even if it stops receiving heartbeats from some of the service instances. This prevents the Eureka server from 
                               evicting all the instances due to temporary network glitches or delays.
                             - In Self-Preservation mode, the Eureka server continues to serve the registered instances to client applications, even if it suspects that
                               some instances are no longer available. This helps maintain the stability and availability of the service registry, ensuring that clients
                               can still discover and interact with the available instances. 
                             - Self-preservation mode never expires, until and unless the down microservices are brought back or the network glitch is resolved. This is
                               because eureka will not expire the instances till it is above the threshold limit.

                        - NOTE:- Eureka Server will not panic when it is not receiving heartbeats from majority of the instances, instead it will be calm and enters 
                                 into Self-preservation mode. This feature is a savior where the networks glitches are common and help us to handle false-positive 
                                 alarms.
                             - look mandan reddy notes for diagram visual.
                             - Configurations which will directly or indirectly impact self-preservation behavior of eureka :
                                      - eureka.instance.lease-renewal-interval-in-seconds = 30
                                           Indicates the frequency the client sends to server to indicate that it is still alive
                                      - eureka.instance. lease-expiration-duration-in-seconds = 90
                                           Indicates the duration the server waits since it received the last heartbeat before it can evict an instance
                                      - eureka.server.eviction-interval-timer-in-ms = 60 * 1000
                                           A scheduler(EvictionTask) is run at this frequency which will evict instances from the registry if the lease of the instances
                                           are expired as configured by lease-expiration-duration-in-seconds. It will also check whether the system has reached
                                           self-preservation mode (by comparing actual and expected heartbeats) before evicting.
                                      - eureka.server.renewal-percent-threshold = O.85
                                           This value is used to calculate the expected % of heartbeats per minute eureka is expecting.
                                      - eureka.server.renewal-threshold-update-interval-ms = 15 * 60 * 1000
                                           A scheduler is run at this frequency which calculates the expected heartbeats minute
                                      - eureka.server.enable-self-preservation = true
                                           By default self-preservation mode is enabled but if you need to disable it you can change it to 'false'
